## A. Joins (Combine Data across Tables)

- A **JOIN** brings together related data from two tables.
- If you know user IDs in one table, but you want to see their usernames from another table — here we use joins.

![](2.%20Advanced%20SQL%20queries-1755537439868.webp)

### 1. Inner join

**Use when:** You want only the rows where the relationship exists in both tables.

```sql
SELECT orders.id, orders.amount, users.username
FROM orders
INNER JOIN users ON orders.user_id = users.id;
```

|id|amount|username|
|---|---|---|
|101|150.00|alice|
|102|75.00|alice|
|103|220.50|bob|
- The database looks at every `orders.user_id`, finds the matching `users.id`, then merges the info.
- If someone exists in `orders` but not in `users`, they won’t show.

### 2. LEFT JOIN

**Use when:** You want ALL rows from the "left" table (here, `users`), even if there’s NO matching data in the "right" table (`orders`).

```SQL
SELECT users.username, orders.id AS order_id, orders.amount
FROM users
LEFT JOIN orders ON users.id = orders.user_id;
```

|username|order_id|amount|
|---|---|---|
|alice|101|150.00|
|alice|102|75.00|
|bob|103|220.50|
|charlie|NULL|NULL|

**Explanation:**

- Shows all users, even `charlie` who has no orders (his order fields are NULL).
- Great for reports like "Which users still haven’t bought anything?"

## B. Aggregations: Calculating Totals, Counts, and More

Sometimes you don’t want the raw data—you want **summaries**, such as totals, averages, or how many orders someone made.

---

### 1. GROUP BY and SUM: Total Spent Per User

```SQL
SELECT users.username, SUM(orders.amount) AS total_spent
FROM users
JOIN orders ON users.id = orders.user_id
GROUP BY users.username;
```

|username|total_spent|
|---|---|
|alice|225.00|
|bob|220.50|

**Explanation:**

- For each unique username, add up (`SUM`) all their orders’ amount.
- No entry for `charlie`—he’s never ordered (JOIN finds no orders for him).

### 2. HAVING: Filter Groups

**What if you want only users who made more than 1 order?**

```sql
SELECT users.username, COUNT(orders.id) AS order_count
FROM users
JOIN orders ON users.id = orders.user_id
GROUP BY users.username
HAVING COUNT(orders.id) > 1;
```

|username|order_count|
|---|---|
|alice|2|

**Explanation:**

- `GROUP BY` splits results by username.
- `COUNT` counts their orders.
- `HAVING` acts like a WHERE but applies AFTER grouping.
- Only users who’ve made more than 1 order show up.

## C. Subqueries: Using a Query Inside Another

**When do you need subqueries?**
- Whenever you need a result that depends on another search.

**Example:** Find users who spent over $200 in total.

```sql
SELECT username
FROM users
WHERE id IN (
    SELECT user_id
    FROM orders
    GROUP BY user_id
    HAVING SUM(amount) > 200
);
```

|username|
|---|
|alice|
|bob|

**Explanation:**
- The subquery inside `IN` finds all `user_id`'s whose total order amount is >200.
- The outer query fetches those users’ usernames.

## D. Common Table Expressions (WITH)

A **Common Table Expression (CTE)** lets you create a "temporary table" (just for a query).

**Get each user’s order count, then display alongside usernames:**

```sql
WITH user_orders AS(
	SELECT user_id, COUNT(*) AS order_count
	FROM orders
	GROUP BY user_id
)
```

```sql
SELECT users.username, user_orders.order_count
FROM users
JOIN user_orders ON users.id = user_orders.user_id;
```


| username | order_count |
| -------- | ----------- |
| alice    | 2           |
| bob      | 1           |
## E. Window Functions: Calculations That “Look” Across Rows

**Example: Show a user’s running total spend, in order of their purchases.**

```sql
SELECT users.username, orders.amount,
       SUM(orders.amount) OVER (PARTITION BY users.id 
	   ORDER BY orders.order_date) AS running_total
FROM users
JOIN orders ON users.id = orders.user_id;
```

|username|amount|running_total|
|---|---|---|
|alice|150.00|150.00|
|alice|75.00|225.00|
|bob|220.50|220.50|

- For each user, order their purchases by date, and `SUM` the amounts so far.
- This is great for analytics—like plotting a user’s growth or progress.

## F. Transactions: Making Changes Safely

- **A transaction** groups changes together to ensure all-or-nothing behavior.
- Useful if an operation needs several steps and you can’t allow partial updates—e.g., transferring money.

**Transaction Workflow:**

```sql
BEGIN;

UPDATE accounts SET balance = balance - 50 
WHERE id = 1;

UPDATE accounts SET balance =  balance + 50
WHERE id = 2

COMMIT;
```

- If anything fails after `BEGIN;` but before `COMMIT;`, you run `ROLLBACK;` and the database undoes all changes in this block.

## SUMMARY

- **JOINS** link your data.

- **Subqueries and CTEs** help organize complex logic.
- **Window functions** perform running calculations.
- **Transactions** keep things safe.
