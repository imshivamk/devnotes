- **Authorization:** What are you allowed to do? (protect endpoints based on roles or permissions)

- Authorization determines what authenticated users are allowed to do in a backend system.
- After a user is authenticated—meaning their identity is confirmed—authorization policies dictate which resources and actions they can access or perform. 
- This is a distinct step from authentication, which only establishes user identity; 
- authorization defines access and permissions based on that identity.
## Common Authorization Patterns

**1. Role-Based Access Control (RBAC)**

- **What it is:** RBAC is a widely used approach where permissions are grouped into roles (e.g., user, admin, editor), and users are assigned one or more roles.
- **How it works:** Each role comes with a set of permissions. Backend logic checks the authenticated user's role(s) before granting access to a route, resource, or functionality. For example, only users with the `admin` role can delete resources.
    
- **Benefits:**
    
    - **Simplicity:** Easier permission management—modify a role to affect many users.
    - **Security:** Enforces the principle of least privilege by assigning only necessary permissions.
    - **Auditing:** Easier to review who has what access and to adjust roles as needed

- **Implementation tip:** Roles and permissions can be encoded in access tokens (such as JWTs) or managed through a database lookup on every request.
    

**2. Attribute-Based and Custom Access Controls**

- Sometimes, access is determined by user properties (attributes), such as department, account status, or subscription level.
- Custom logic can be added to verify if a user’s attributes or states meet the requirements for access.

## JWT-based Authorization

With JWT (JSON Web Token) authentication, authorization often uses data embedded in the JWT payload:

- When the backend verifies a JWT, it can extract the user’s roles or permissions directly from the token.
    
- This enables stateless authorization, as every request carries its own verifiable claims[6](https://jwt.io/introduction).
    

**Security and Best Practices:**

- **Verify all claims:** Always validate tokens against expected issuers (`iss`), audiences (`aud`), and use only tokens with appropriate scopes or roles for protected endpoints.
    
- **Short-lived tokens:** Set short expiration times for JWTs to reduce risk if a token is leaked.
    
- **Principle of least privilege:** Grant users only the permissions/roles strictly necessary for their tasks.
    
- **Do not include sensitive data in tokens:** Only store non-confidential authorization details like roles or permissions[7](https://curity.io/resources/learn/jwt-best-practices/)[8](https://snyk.io/blog/top-3-security-best-practices-for-handling-jwts/)[9](https://zerothreat.ai/blog/json-web-token-jwt-security-best-practices).
    
- **Centralized permission checks:** Apply authorization middleware or checks to all protected routes, not just some.
    

**Sample Flow:**

1. User logs in and receives a JWT containing their roles/permissions.
2. The client includes the JWT in each request.
3. The backend verifies the JWT and authorizes the requested action based on the encoded roles/permissions.

## Summary Table: Authorization Concepts

|Concept|Description|
|---|---|
|**RBAC**|Assigns permissions to roles; users assigned to roles|
|**Claims-based**|Uses data in JWT (roles, scopes, etc.) for access decisions|
|**Least Privilege**|Only grant permissions absolutely necessary|
|**Central Checks**|Authorize in a middleware or handler for each sensitive route/resource|
|**Short-lived JWT**|Use tokens with near-term expiration for security|
