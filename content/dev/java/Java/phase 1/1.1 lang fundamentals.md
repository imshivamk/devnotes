
## 1. Primitives vs. wrapper classes

Java has two representations of common values.

```java
int age = 25;          // primitive
Integer boxedAge = 25; // wrapper object
```

A primitive stores the value directly. A wrapper stores a reference to an object containing the value.

```text
int age = 25

Stack
+----------+
| age = 25 |
+----------+
```

```text
Integer boxedAge = 25

Stack                         Heap
+----------------+            +------------------+
| boxedAge ----- |-----------> | Integer object  |
+----------------+            | value = 25      |
                              | object header   |
                              +------------------+
```

The exact stack and heap behavior is an implementation model; the JVM may optimize objects using escape analysis. However, this model is useful for interviews.

### When to use each

Use primitives when:

- The value is always present.
- Performance or memory usage matters.
- You are processing large arrays or hot loops.

```java
int[] values = new int[1_000_000];
```

Use wrappers when:

- `null` has meaning.
- A generic type is required.
- A framework or collection expects objects.

```java
List<Integer> values = new ArrayList<>();
Integer missingValue = null;
```

A `List<int>` is illegal because Java generics work with reference types.

### `int[]` versus `Integer[]`

```java
int[] a = new int[3];
Integer[] b = new Integer[3];
```

`int[]` stores three primitive values directly:

```text
int[]:      [ 0 ][ 0 ][ 0 ]
```

`Integer[]` initially stores three null references:

```text
Integer[]:  [ null ][ null ][ null ]
```

After boxing:

```java
b[0] = 10;
```

the array contains a reference to an `Integer` object. This means more memory accesses, possible allocations, and more garbage collection.

## 2. Autoboxing and the `Integer` cache

Autoboxing converts a primitive to a wrapper automatically.

```java
Integer value = 10; // Integer.valueOf(10)
```

Unboxing converts the wrapper back to a primitive.

```java
int number = value; // value.intValue()
```

This is convenient but can hide performance costs.

```java
List<Integer> numbers = new ArrayList<>();
numbers.add(10);             // boxing
int x = numbers.get(0);      // unboxing
```

### Integer caching

The JVM commonly reuses `Integer` objects for values from `-128` through `127`.

```java
Integer a = 127;
Integer b = 127;

System.out.println(a == b);       // true, cached object
System.out.println(a.equals(b));  // true
```

For larger values, separate objects are normally created:

```java
Integer x = 128;
Integer y = 128;

System.out.println(x == y);       // usually false
System.out.println(x.equals(y));  // true
```

`==` compares object references. `.equals()` compares values.

Always write:

```java
x.equals(y)
```

or, if either can be null:

```java
Objects.equals(x, y)
```

The cache size may be adjusted on some JVMs:

```bash
java -XX:AutoBoxCacheMax=1000 MyProgram
```

Do not rely on this behavior for application logic.

### Null unboxing trap

```java
Integer value = null;
int number = value;
```

This becomes approximately:

```java
int number = value.intValue();
```

Because `value` is null, the code throws `NullPointerException`.

### Performance use case

Avoid this in a very hot loop:

```java
Long total = 0L;

for (long value : values) {
    total += value; // unbox, add, box on every iteration
}
```

Prefer:

```java
long total = 0L;

for (long value : values) {
    total += value;
}
```

## 3. Java is pass-by-value

Java always passes arguments by value.

For an object, the value being copied is the reference.

```java
class Person {
    String name;
}
```

```java
static void changeName(Person person) {
    person.name = "Bob";
}

Person p = new Person();
p.name = "Alice";

changeName(p);
System.out.println(p.name); // Bob
```

Memory model:

```text
Caller frame                    Method frame
p ----------------+             person -------------+
                  |                              |
                  +----------> same Person object
```

Both variables contain copies of the same reference.

### Mutation is visible

```java
static void mutate(Person p) {
    p.name = "Bob";
}
```

The method changes the shared object.

### Reassignment is not visible

```java
static void replace(Person p) {
    p = new Person();
    p.name = "Charlie";
}

Person original = new Person();
original.name = "Alice";

replace(original);

System.out.println(original.name); // Alice
```

The parameter `p` is reassigned, but the caller’s `original` reference is unchanged.

### Interview explanation

Java does not pass objects by reference. It passes object references by value.

That distinction explains why:

- Object field mutation is visible to the caller.
- Reassigning a parameter is not visible to the caller.

## 4. Numeric conversions and promotion

### Widening conversion

A smaller numeric type can usually be assigned to a larger type automatically.

```java
int number = 10;
long larger = number;
double decimal = larger;
```

```text
byte → short → int → long → float → double
  char ────────┘
```

Widening normally preserves magnitude, although converting `long` to `float` may lose precision because `float` has fewer significant bits.

### Narrowing conversion

A larger type requires an explicit cast.

```java
double price = 3.99;
int whole = (int) price;

System.out.println(whole); // 3
```

The fractional portion is discarded; this is truncation, not rounding.

```java
int rounded = (int) Math.round(price); // 4
```

### Bit wrapping

```java
long value = Long.MAX_VALUE;
int result = (int) value;

System.out.println(result); // -1
```

An `int` has 32 bits. The lower 32 bits of `Long.MAX_VALUE` are all `1`, which represents `-1` in signed two’s-complement form.

### Binary numeric promotion

Small integer types are promoted to `int` during arithmetic.

```java
byte a = 10;
byte b = 20;

byte result = (byte) (a + b); // required cast
int sum = a + b;              // normal result type is int
```

This fails:

```java
byte result = a + b; // compile error
```

because `a + b` produces an `int`.

## 5. String pool and allocation

String literals are stored in the string pool.

```java
String first = "hello";
String second = "hello";

System.out.println(first == second); // true
```

Both variables refer to the same pooled object.

```java
String third = new String("hello");

System.out.println(first == third);      // false
System.out.println(first.equals(third)); // true
```

`new String("hello")` explicitly creates another `String` object, even though `"hello"` already exists in the pool.

Conceptually:

```text
String first = "hello"

first --------------------+
                           v
                    pooled String("hello")
```

```text
String third = new String("hello")

third --------------------> new String object
                              |
                              +--> character/byte data
```

The implementation may share internal data or use compact strings, so this is a conceptual diagram rather than a guaranteed physical layout.

### `intern()`

```java
String a = new String("hello");
String b = a.intern();

System.out.println(b == "hello"); // true
```

`intern()` returns the canonical pooled instance.

Use `intern()` carefully. Excessive interning can increase memory pressure and usually is not needed in ordinary application code.

## 6. Why `String` is immutable

Once created, a `String` cannot change.

```java
String text = "hello";
text.toUpperCase();

System.out.println(text); // hello
```

The method returns a new string:

```java
text = text.toUpperCase();
```

### Security use case

Suppose a security check validates a path:

```java
String path = getPath();
if (path.startsWith("/safe/")) {
    openFile(path);
}
```

If strings were mutable, another reference could modify `path` after validation but before use. Immutability prevents this type of time-of-check/time-of-use problem.

The same principle helps with:

- Class names
- File paths
- Network hostnames
- Database connection strings
- Authentication tokens

### Hash-code caching

Strings are frequently used as map keys. Because they cannot change, a string may safely cache its hash code.

Conceptually:

```java
private int hash;
```

If the contents never change, the cached hash remains correct. This is also safe when multiple threads read the string concurrently.

### Why `String` is final

```java
class CustomString extends String {
}
```

This does not compile because `String` is `final`.

Making it final prevents subclasses from changing important behavior such as immutability, equality, hashing, or security-sensitive methods.

## 7. String concatenation

This code may repeatedly create new strings:

```java
String result = "";

for (int i = 0; i < 10_000; i++) {
    result += i;
}
```

Strings are immutable. Each concatenation may copy the previous contents, producing approximately quadratic work:

```text
copy 1 character
copy 2 characters
copy 3 characters
...
```

Use `StringBuilder` for repeated construction:

```java
StringBuilder builder = new StringBuilder();

for (int i = 0; i < 10_000; i++) {
    builder.append(i);
}

String result = builder.toString();
```

`StringBuffer` performs similar operations but synchronizes its methods. Use it only when that synchronization is specifically needed.

The traditional capacity formula is:

```text
new capacity = old capacity * 2 + 2

16 → 34 → 70 → 142
```

Modern Java compilers often use `invokedynamic` for runtime string concatenation:

```java
String result = name + age;
```

Compile-time constants are folded:

```java
String result = "a" + "b" + "c";
// effectively "abc"
```

## 8. `==`, `.equals()`, and equality contracts

Use:

```java
==          // primitive values or reference identity
.equals()  // logical object equality
```

Examples:

```java
"abc" == new String("abc")       // false
"abc".equals(new String("abc"))  // true
```

For a custom class:

```java
final class Person {
    private final String name;
    private final int age;

    Person(String name, int age) {
        this.name = name;
        this.age = age;
    }

    @Override
    public boolean equals(Object object) {
        if (this == object) return true;
        if (!(object instanceof Person other)) return false;

        return age == other.age &&
               Objects.equals(name, other.name);
    }

    @Override
    public int hashCode() {
        return Objects.hash(name, age);
    }
}
```

`equals()` should be:

- Reflexive: an object equals itself.
- Symmetric: `a.equals(b)` equals `b.equals(a)`.
- Transitive.
- Consistent while relevant state is unchanged.
- False when compared with `null`.

Use null-safe expressions:

```java
"ACTIVE".equals(status)
```

instead of:

```java
status.equals("ACTIVE")
```

if `status` could be null.

## 9. `equals()` and `hashCode()`

The key contract is:

```text
a.equals(b) == true
⇒ a.hashCode() == b.hashCode()
```

The reverse is not required. Two unequal objects may have the same hash code; that is a collision.

A `HashMap` approximately performs:

```java
int bucket = (capacity - 1) & hash;
```

This works efficiently when the capacity is a power of two.

### Mutable-key failure

```java
class User {
    String username;

    @Override
    public int hashCode() {
        return username.hashCode();
    }
}
```

```java
User user = new User();
user.username = "alice";

Map<User, String> map = new HashMap<>();
map.put(user, "data");

user.username = "bob";

System.out.println(map.get(user)); // may be null
```

The object was inserted into the bucket for `"alice"`, but lookup now searches the bucket for `"bob"`.

Use immutable keys whenever possible.

## 10. `final`, `volatile`, and `transient`

### `final` reference

```java
final List<String> names = new ArrayList<>();
names.add("Alice"); // valid
```

The reference cannot point to a different list:

```java
names = new ArrayList<>(); // compile error
```

But the list itself remains mutable.

### `volatile`

```java
private volatile boolean running = true;

void stop() {
    running = false;
}

void work() {
    while (running) {
        doWork();
    }
}
```

`volatile` ensures that one thread sees updates made by another thread.

It does not make compound operations atomic:

```java
volatile int count;
count++; // read, add, write — not atomic
```

Use `AtomicInteger` or synchronization for counters.

### `transient`

```java
class Account implements Serializable {
    String username;
    transient String password;
}
```

The `password` field is skipped by default Java serialization. This is not a complete security strategy; avoid serializing sensitive data whenever possible.

## 11. Varargs

```java
static void printAll(String... values) {
    for (String value : values) {
        System.out.println(value);
    }
}
```

The compiler treats this approximately as:

```java
static void printAll(String[] values)
```

Calls create arrays:

```java
printAll();             // new String[0]
printAll("one");        // new String[]{"one"}
printAll("one", "two"); // new String[]{"one", "two"}
```

Varargs create an array at the call site, so avoid them in extremely hot code if allocation matters.

Generic varargs can be unsafe because arrays know their runtime component type while generics are erased:

```java
@SafeVarargs
static <T> void process(List<T>... lists) {
    // Use only when the implementation is genuinely safe.
}
```

## 12. Bitwise operators

```java
int bit = (number >> position) & 1;
```

This extracts one bit.

For example, if:

```text
number = 13 = 1101₂
```

then:

```java
(13 >> 2) & 1
```

extracts the third bit from the right.

### Right shifts

```java
int value = -8;

value >> 1;   // -4; sign bit is copied
value >>> 1;  // large positive value; zeros are inserted
```

Use `>>` when preserving signed meaning. Use `>>>` when treating the value as an unsigned bit pattern.

### Masking

```java
int lowerFourBits = number & 0b1111;
```

This keeps only the lowest four bits.

The expression:

```java
hash & (capacity - 1)
```

selects a HashMap bucket when the capacity is a power of two.

## 13. Access modifiers

| Modifier | Same class | Same package | Subclass elsewhere | Unrelated class |
|---|---:|---:|---:|---:|
| `private` | Yes | No | No | No |
| package-private | Yes | Yes | No | No |
| `protected` | Yes | Yes | Yes, with inheritance rules | No |
| `public` | Yes | Yes | Yes | Yes |

`protected` across packages is often misunderstood. A subclass can access the member through inheritance, but arbitrary access through an unrelated superclass instance is restricted.

Use:

- `private` for implementation details.
- Package-private for package-internal collaboration.
- `protected` sparingly for designed extension points.
- `public` for stable external APIs.

## 14. Constructors and initialization

```java
class Parent {
    Parent() {
        System.out.println("Parent constructor");
    }
}

class Child extends Parent {
    Child() {
        super();
        System.out.println("Child constructor");
    }
}
```

Output:

```text
Parent constructor
Child constructor
```

A constructor must begin with either:

```java
this(...);
```

or:

```java
super(...);
```

If omitted, Java inserts `super()` when possible.

Constructors are not inherited because constructing a subclass requires subclass-specific initialization.

The general initialization order is:

1. Static initialization of the superclass.
2. Static initialization of the subclass.
3. Instance initialization of the superclass.
4. Superclass constructor.
5. Instance initialization of the subclass.
6. Subclass constructor.

## 15. Scope and lifetime

```java
class Example {
    static int staticField;  // associated with the class
    int instanceField;       // associated with an object

    void method(int parameter) {
        int local = 10;

        if (local > 0) {
            int blockLocal = 20;
        }
    }
}
```

- A parameter exists during the method call.
- A local variable exists within its method or block.
- An instance field exists while its object is reachable.
- A static field exists while its class is loaded and initialized.

A method call receives a stack frame containing parameters, local variables, and the operand stack. Objects and arrays generally live on the heap, although the JVM may optimize allocations.

## 16. Date and time

Prefer `java.time` over `Date` and `Calendar`.

```java
LocalDate date = LocalDate.of(2026, 9, 29);
LocalDateTime localDateTime = LocalDateTime.now();
Instant instant = Instant.now();
ZoneId zone = ZoneId.of("Europe/London");
```

Use the types according to meaning:

- `LocalDate`: date without time zone, such as a birthday.
- `LocalDateTime`: date and time without zone; suitable only when a zone is not relevant.
- `Instant`: absolute moment in UTC.
- `ZonedDateTime`: moment plus time zone.
- `Duration`: elapsed seconds/nanoseconds.
- `Period`: calendar days, months, or years.

For backend timestamps, prefer:

```java
Instant createdAt = Instant.now();
```

Convert only when displaying:

```java
ZonedDateTime local =
    createdAt.atZone(ZoneId.of("America/New_York"));
```

Parsing:

```java
Instant timestamp =
    Instant.parse("2026-09-29T12:00:00Z");
```

## 17. `BigDecimal` and money

Binary floating-point values cannot exactly represent most decimal fractions.

```java
System.out.println(0.1 + 0.2);       // 0.30000000000000004
System.out.println(0.1 + 0.2 == 0.3); // false
```

Prefer:

```java
BigDecimal amount = new BigDecimal("19.99");
```

or:

```java
BigDecimal amount = BigDecimal.valueOf(19.99);
```

Avoid:

```java
new BigDecimal(0.1);
```

because it captures the already-imprecise binary representation of `0.1`.

Rounding should be explicit:

```java
BigDecimal rounded =
    amount.setScale(2, RoundingMode.HALF_UP);
```

For an API, include currency:

```java
record Money(BigDecimal amount, Currency currency) {}
```

For a single known currency, minor units can be stored as `long`:

```java
long cents = 1999; // $19.99
```

For multiple currencies, always store:

- Amount
- Currency code
- Exchange rate
- Rate source
- Rate timestamp
- Rounding policy

Never compare or add monetary values from different currencies without conversion.
