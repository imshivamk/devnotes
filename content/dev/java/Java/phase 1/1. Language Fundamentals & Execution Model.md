# 1. The Stack vs. The Heap Breakdown

JVM splits data allocation into

1. **The JVM Stack (Thread-Isolated Memory):**
    
    - Every single thread in a Java application has its own dedicated, private Stack.
        
    - When a method is called, a **Stack Frame** is pushed onto the stack. This frame stores local variables and parameters.
        
    - Primitives declared inside a method live entirely inside this Stack Frame.
        
    - **Mechanics:** Accessing memory from the Stack is incredibly fast. The CPU moves down sequentially; there are no complex pointer translations, and cleanup is automatic. When the method finishes execution, its stack frame is popped off, and that memory space instantly disappears.

2. **The JVM Heap (Shared Application Memory):**
    
    - The Heap is a massive global pool of memory shared by all threads.
        
    - **All objects**—no matter where they are instantiated—live on the Heap.
        
    - Wrapper classes (`Integer`, `Long`, `Boolean`, etc.) are full objects. Therefore, they live on the Heap.
        
    - When you declare `Integer score = 100;` inside a method, an 8-byte reference pointer (`score`) is placed on your local stack frame, but that pointer holds a memory address pointing to the actual `Integer` object residing out on the shared Heap.

![](1.%20Language%20Fundamentals%20&%20Execution%20Model-1782563085938.webp)

#### Memory Layout & The Performance Cost

- **Raw Primitives:** An `int` variable takes exactly **4 bytes (32 bits)** of raw space. It has no metadata, no object identifier, just raw binary data.
    
- **Wrapper Objects:** On a standard 64-bit production JVM, an `Integer` object takes **24 bytes** of memory.
    
    - **12 to 16 Bytes** are consumed instantly by the **Object Header**. This header consists of the _Mark Word_ (storing identity hashcodes, locking states, and garbage collection flags) and the _Klass Word_ (a pointer back to the class metadata).
        
    - **4 Bytes** store the actual primitive value.
        
    - **Padding:** The JVM rounds object allocations to the nearest multiple of 8 bytes. Thus, a 16 or 20-byte footprint gets padded up to a full **24 bytes**.
    - The rule of thumb that primitives live on the stack only applies to local variables declared inside method scopes. 
    - When a primitive is an instance variable of an object, it is stored physically inside the structure of that object on the heap. 
    - The variable `p` on the stack is simply an 8-byte reference holding the address of that `Point` object payload."

### unboxing and autoboxing 

When performing math on wrapper classes in a loop, Java is forced to perform an invisible step called **Unboxing** to read the value, do the calculation on the CPU, and then perform **Autoboxing** (allocating a whole new `Integer` object on the heap) to save the result.

This causes constant pointer dereferencing into the Heap, completely blowing out your CPU's L1/L2 cache locality and generating massive amounts of garbage collection overhead.


# 2. autoboxing/unboxing and Integer cache pool

- **Autoboxing:** Converting a primitive to a wrapper. When you write `Integer val = 10;`, the compiler intercepts your code at compile-time and transforms it into bytecode that executes: `Integer val = Integer.valueOf(10);`.
    
- **Unboxing:** Converting a wrapper to a primitive. When you write `int raw = val;`, the compiler rewrites it as: `int raw = val.intValue();`.

#### Flyweight Pattern (The Integer Cache)

Instantiating objects on the heap is expensive. Because small numbers (like `-1`, `0`, `1`, `50`) are used constantly across applications, Java engineers applied the **Flyweight Design Pattern** directly into the `Integer` class.

When the JVM boots up, an internal static cache array inside the `Integer` class is allocated on the heap. By default, this array pre-instantiates and caches **all Integer objects representing values from `-128` to `127` (inclusive)**.

When you call `Integer.valueOf(x)` (either explicitly or via implicit autoboxing):

1. The method checks if `x >= -128` and `x <= 127`.
    
2. **If it matches:** It does **not** create a new object. It returns a reference to the pre-existing object already living in the cache pool.
    
3. **If it does not match:** It bypasses the cache and executes a standard `new Integer(x)`, creating a completely brand-new object on the heap.

Therefore,
```java
Integer a = 10;
Integer b = 10;
// Both point to the same object

Integer x = 200;
Integer y = 200;
// both point to different objects in the heap
```

The JVM implements cache pools across other data primitives as well:

- you can modify the upper bound of the Integer cache using the JVM configuration flag `-XX:AutoBoxCacheMax=<size>`
- In backend systems that handle a massive number of small ID processing transactions (for example, reading values between `1` and `5000` constantly from a database), increasing this cache limit keeps those numbers pooled, reducing heap allocation thrashing and stabilizing garbage collection latency
# 3. Pass-by-Value vs. Pass-by-Reference

- Java handles objects via pointers, but **Java is strictly 100% Pass-by-Value**
- java separates **the Object itself** from **the Reference Variable** pointing to it.

1. **The Reference Variable:** When you write `User u = new User("Shivam");`, `u` is not the actual user object. `u` is a variable on the stack frame that holds a 64-bit hexadecimal memory address (e.g., `0x7A4F`) pointing to the heap.
    
2. **The Method Invocation:** When you pass `u` into a method via `processUser(u);`, the JVM allocates a completely new variable slot inside the new method's stack frame. It then **copies the bits** of the value inside `u`.
    
3. **The Result:** The new stack frame now contains a copy of the memory address `0x7A4F`. Both variables are independent copies, but they happen to point to the exact same physical object on the heap.

> we can still mutate the object's properties, because even if its being copied into another variable, the address is the same. so changed made will be reflected.

> we cannot reassign the reference itself. 

#interview 
>Java passes the value of the variable by copying bits. For a primitive, the value is the literal numeric data itself, so modifications remain local to that stack frame. For an array or object, the value inside the variable is the memory address pointer. Java copies this reference pointer into the new stack frame. Because both references now point to the same array heap allocation, modifying `arr[0]` updates the shared state, whereas reassigning `arr = new int[5]` has no effect on the caller.



# 4. Type casting

Java's primitve hierarchy : 
$$
\text{byte (1B)} \rightarrow \text{short (2B)} \rightarrow \text{char (2B)} \rightarrow \text{int (4B)} \rightarrow \text{long (8B)} \rightarrow \text{float (4B)} \rightarrow \text{double (8B)}

$$

#### 1. Widening Primitive Conversion (Implicit Casting)

- **Mechanics:** Occurs automatically when a smaller data type is assigned to a larger data type register.
    
- **Safety:** Safe from a scale perspective (e.g., an `int` easily fits into a 64-bit `long` register).
    
- **The Precision Catch:** While moving an `int` or `long` to a `float` or `double` is automatic, it can cause a silent **loss of precision**. 
- A `long` uses all 64 bits for magnitude, but a `float` or `double` allocates parts of its bits to exponents and mantissas (IEEE 754 standard).
- As a result, very large integers can lose their least significant bits when converted to floating-point numbers without generating an explicit error.


#### 2. Narrowing Primitive Conversion (Explicit Casting)

- **Mechanics:** Requires manual intervention using syntax instructions, such as `int x = (int) myLong;`.
    
- **Risk Profile:** Unsafe. It instructs the compiler to forcefully strip away the upper bits of a value, which frequently results in data loss or structural sign changes.

#### 3. Low-Level Binary Mechanics of Truncation

When you explicitly narrow an 8-byte `long` or a 4-byte `int` into a 1-byte `byte`, the JVM physically clips off the higher-order bytes and keeps only the **lowest 8 bits**.

- **The Two's Complement Trapped Sign:** Because Java integers are signed and use two's complement representation, if the highest remaining bit of that truncated 8-bit slice happens to be a `1`, the JVM interprets the final value as a **negative number**, even if the original value was a massive positive integer.

- **Floating-Point to Integer:** Converting a `float` or `double` to an `int` completely drops the decimal portion (truncation toward zero). If the floating-point value exceeds the maximum capacity of an `int`, the variable clamps directly to `Integer.MAX_VALUE` ($2,147,483,647$) or `Integer.MIN_VALUE`.

>Java performs all binary arithmetic operations using a minimum register width of 32 bits for evaluation safety. When evaluating `b1 + b2`, the JVM implicitly promotes both operands to `int` values before performing the addition

# 5. String pool elaboration

- to prevent string duplication java keeps a string constant pool
#### 1. Creating Strings: The Two Different Roads

The way you create a String determines whether Java uses this optimized pool or forces a brand-new object onto the general memory heap:

- **Road A: Using String Literals (The Smart Way)**
    
    Java
    
    ```
    String s1 = "VJTI";
    ```
    
    When you declare a string like this, Java checks the String Pool first.
    
    - If the letters `"VJTI"` are **already in the pool**, Java simply gives your variable a pointer to that existing object.
        
    - If they aren't there yet, Java creates a single copy in the pool. No duplicate objects are ever made.
        
- **Road B: Using the `new` Keyword (The Manual Way)**
    
    Java
    
    ```
    String s2 = new String("VJTI");
    ```
    
    Using the `new` keyword forces Java to bypass pool lookup optimizations. It explicitly builds a **brand-new, independent String object** out in the general heap memory space, even if the exact same letters already exist in the pool.
    

#### What does `==` actually do?

In Java, when you use `==` between two objects, you are checking if they point to the **exact same spot in memory (same reference)**. You are _not_ checking if the text inside them matches (for text matching, you always use `.equals()`).


```java
String s4 = s2.intern();
```

The `.intern()` method looks at the text inside `s2` (`"VJTI"`), goes to the String Pool, finds the matching version, and returns a direct pointer to that pool object. Now, `s1 == s4` will evaluate to `true`!


when "new" keyword is used, java explicitly creates a new object on the heap. also if the newly created string is not available in the string constant pool, a new entry in the string pool is also created, so total 2 objects are created.

# 6. String immutability

In Java, **Strings are completely immutable**. This means that once a String object is built in memory, its text value **can never be changed**.

  
If you attempt to modify a string—such as converting it to uppercase or attaching additional words to it—Java does not change the characters inside the original object. Instead, it leaves the original object exactly as it is and creates a **brand-new String object** somewhere else in memory to hold the updated text.

#### A. The String Pool Optimization (Saving Memory)

Because strings are used everywhere in code, creating a new object for every duplicate string would quickly eat up all your computer's memory. Because strings are unchangeable, Java can safely use the **String Pool**.

If ten different variables declare `String location = "Mumbai";`, Java only creates **one** single `"Mumbai"` object in memory. All ten variables point to the exact same spot. This only works because Java guarantees that no one can change that object.

#### B. Thread-Safety (Zero Concurrency Errors)

In modern backend systems, multiple threads (separate processes running at the same time) often read the same data simultaneously.

- If a String could change, Thread A might be halfway through reading a user's address while Thread B suddenly alters it. This causes data corruption and bugs.
    
- Because strings cannot be modified, multiple threads can safely read the same String simultaneously without using complex synchronization locks.
    

#### C. Absolute Security

Strings handle the most critical information in your application: database passwords, network URLs, file system paths, and cloud authorization codes.

Imagine if strings were mutable. Your application might check a string variable containing a file path to confirm it is safe to open. Right after the security check passes, a malicious background thread could mutably alter the characters inside that exact same string object to point to a restricted system file. Immutability completely closes this vulnerability.


#interview 
```
- **Interviewer:** _"If Strings are completely safe and immutable, why do security-focused features (like bank passwords or credit card inputs) use a primitive character array (`char[]`) instead of a regular `String`?"_
    
- **Candidate Response:** _"Even though you cannot change a String object in code, its data stays in the computer's memory until Java's automatic Garbage Collector decides to clean it up later. This means a sensitive password could sit exposed in memory for a long time. A primitive `char[]` array, however, allows us to manually overwrite its slots with zeros (`'0'`) or blank spaces the exact millisecond we are done checking the password, completely wiping it from memory immediately."_
```



```java
import java.util.Arrays;

public final class UserSession { // Marked final so nobody can subclass it
    private final String username;
    private final String accessLevel;
    private final String[] permissions;

    public UserSession(String username, String accessLevel, String[] permissions) {
        this.username = username;
        this.accessLevel = accessLevel;
        
        // 1. DEFENSIVE COPY ON INPUT: Clone the array so the outside world loses its handle
        this.permissions = (permissions == null) ? new String[0] : permissions.clone();
    }
    
    public String getUsername() { return username; }
    public String getAccessLevel() { return accessLevel; }

    public String[] getPermissions() {
        // 2. DEFENSIVE COPY ON OUTPUT: Never hand out the real array address pointer
        return this.permissions.clone();
    }
}
```
Using `.clone()` builds a completely separate array block in memory, ensuring your class stays safe from unexpected changes.


# 7. StringBuilder vs StringBuffer

**StringBuilder / StringBuffer:** These classes act as a expandable, elastic workspace. They maintain a single, internal resizable array of characters. When you call `.append()`, Java drops the characters straight into the existing workspace without generating trash objects.

StringBuilder is not thread safe, but is fastest at modifying or assembling text loops in a single process thread.

StringBuffer is thread-safe, syncronised, slower as it has locks. used in legacy apps where multiple threads write to one string buffer.
